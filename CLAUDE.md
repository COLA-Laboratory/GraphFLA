# GraphFLA — project guidance

This is the repository for GraphFLA, a Python package for fitness landscape analysis. The high-level expectation for this package is that it can calculate landscape statistics (e.g., ruggedness) for arbitary combinatorial optimization problems in different fields (e.g., classical combinatorial optimization, hyper-parameter optimization in machine learning (though in a discretized form), chemical engineering, or protein engineering, etc.).

Essentially, a fitness landscape is just referring to the mapping from X \to f, where X is the search space, and f is whatever objective function that we are interested in (e.g., model performance, reaction yields, thermostability of protein, etc.). So this package should be agnostic to the context of problems, which is similar to sklearn, which also mainly deals with datasets in the shape of (X, f) and does not care about what does X and f represent, though it allows continuous variables.

To conduct fitness landscape analysis, there are primarily two stages, one is landscape construction, where we have to infer the neighborhood structure in the geometric space from the un-ordered set of inputs (in which x \in X in most cases are not ordered by geometrical relationships). We have general landscape classes that would work for all legal combinatorial datasets, and we also have specialized classes for binary, protein, DNA, and RNA data to maximize performance. This landscape construction phase can be time-consuming if naively implemented. We've tried multiple rounds of performance optimization but we are not sure whether we have reached the ceiling. In addition, we also need to make sure that the construction algorithm is correct (i.e., it will not assign wrong neighbors to x \in X) and robust (e.g., behaving correctly even under tricky/rare/boundary cases, as long as the inputs are legal).

Once we have the landscape objects constructed, then GraphFLA provides a suite of analysis functions to explore the landscape topography. These analyses are mostly sourced from established papers in either evolutaionary biology or evolutionary computation community. The ultimate consideration for these analyses are, just like numpy, to ensure that the statistics are correctly calculated. Researchers will rely on our package to analyze their data and publish on prestigious journals. So it is absolutely not acceptable if a statistic is wrongly calculated. That would destroy the user trust and scientific rigor of this package.

When working on this package. You should always make important reasoning/decisions on your own. Sub-agents are only allowed for non-editing/non-essential tasks with clear objectives (e.g., agent 1: "find me papers implementing the r/s ratio", agent 2-N: "read this paper, and tell me how does the author calculate the r/s ratio, quote and never write your own inference", agent M: "help me to download the dataset in this paper and see whether the available artifacts can reproduce the resutls on r/s ratio", and then the actual editing of the GraphFLA project, e.g., adding a validation test of the r/s ratio in GraphFLA using the artifact from a referenced paper, should be your task!). This is just like presidential campaigns – all the stuff in the team can help the candidate to source information, and write media, or even do some work, but the one eventually giving speech to the voters should be the candidate themselves. For sub-agents, always use Opus 5.5 (high).

So the first stuff you got to do in this project is to establish these validation tests. Basic tests can come from very small, hand-written data (to ensure fast tests) that nearly enumerated all types (you can imagine that a unimodal 10,000 variant landscape is not different from a unimodal 8 vairant landscape in terms of testing, so save efforts) of cases (i.e., high coverage) that user can input. And more importantly, like the examples I gave you, try to find cases in real literature (I can download the PDFs for you, all you need is to give me the list of URLs and let me know where should I put those PDFs), and see whether GraphFLA can exactly reproduce their results using the same data (for example, the DHFL landscape by Papkou 2023 published on Science has 514 local optima, and GraphFLA can exactly reproduce following their preprocessing method described in the supplementary material). You will use these two types of tests to constitute a holistic test suite that would ensure the correctness and robustness of GraphFLA.

The next thing you got to work on is performance optimization. That is, conditioned by all those tests (supposing those tests are of 100% coverage) can be passed, try to optimize the performance of the package in terms of both runtime & memory consumption for both the landscape construction & analysis phase (should cover all classes and methods/functions). When doing this optimization, feel free to largely restructure the implementation of code (e.g., the construction phase involves multiple intermediate methods/functions, and used lots of variables, these all can be completely restructured if necessary), as long as the exposed API does not change, and you obey other rules below (e.g., maintainability, extensibility, commenting/doc style, etc.).
